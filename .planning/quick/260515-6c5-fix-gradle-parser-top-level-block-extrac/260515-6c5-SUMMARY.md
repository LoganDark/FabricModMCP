# Phase quick-260515-6c5 Plan 01: Fix Gradle Parser Top-Level Block Extraction Summary

Replaced two non-greedy `/<name>\s*\{([\s\S]*?)\n\}/` regexes in `gradle-parser.ts` with a single brace-tracking helper `extractTopLevelBlock(content, name)` so that a `buildscript { dependencies { classpath(...) } repositories { ... } }` wrapper no longer shadows the real top-level blocks, unblocking real-world Loom projects like AuxCommands-1.21.

## What Changed

- **`src/project/gradle-parser.ts`**
  - Added `extractTopLevelBlock(content: string, name: string): string | null` — character-by-character scan tracking `inString` (with `\`-escape) and `depth`. Locates a block with a depth-0 opening brace where the character before `name` is start-of-string or a non-identifier (preventing `subDependencies {` from matching `name='dependencies'`).
  - `extractMavenRoots` now calls `extractTopLevelBlock(substituted, 'repositories')` and returns `[]` when null; uses the returned body where `repoMatch[1]` was used.
  - `parseBuildGradle` now calls `extractTopLevelBlock(substituted, 'dependencies') ?? ''` for the deps block.
  - The old `/repositories\s*\{([\s\S]*?)\n\}/` and `/dependencies\s*\{([\s\S]*?)\n\}/` regexes are gone (grep returns 0 matches).
- **`tests/project/gradle-parser.test.ts`**
  - Added `describe('buildscript wrapper handling', ...)` with four regression tests:
    - A: top-level deps block extracted past a `buildscript { dependencies { classpath } }` wrapper.
    - B: nested `for (...) { ... }` inside the dependencies block does not prematurely terminate it.
    - C: top-level `repositories { ... }` preferred over `buildscript { repositories { ... } }`.
    - D: `{` / `}` inside string literals (e.g. `"group:artifact:1.0+{weird}"`) do not corrupt depth tracking.
