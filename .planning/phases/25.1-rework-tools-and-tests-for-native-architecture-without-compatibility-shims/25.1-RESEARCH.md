# Phase 25.1: Rework tools and tests for native architecture - Research

**Researched:** 2026-04-15
**Domain:** Internal refactoring — MCP tool API restructuring, compat layer removal, rename propagation
**Confidence:** HIGH

## Summary

This phase is a pure internal refactoring of an existing TypeScript MCP server. No new libraries are needed. The work involves: (1) deleting the compat.ts shim layer and LoadedProject type alias, (2) splitting/renaming 6 tool registrations into 8+ new tools with cleaner separation of concerns, (3) renaming `defaultProject`/`defaultChild` to `activeProject`/`activeChild` throughout codebase, (4) migrating 14 tool files from compat accessor imports to direct child access, and (5) updating all tests to match.

The codebase is well-structured with clear patterns. Every tool follows the same registration pattern (`registerXTool(server: McpServer)`), uses `resolveProjectSafely()` for project resolution, returns `{ content, structuredContent }` envelopes, and imports from centralized `descriptions.ts` and `tool-helpers.ts`. The compat layer is a thin wrapper that calls `getSoleFabricMod()` — migration means replacing those calls with direct `project.children.get(scope)` access, which the scope-aware tools already do.

**Primary recommendation:** Execute as a series of waves: (1) rename `defaultChild`/`defaultProject` to `activeChild`/`activeProject`, (2) delete compat.ts and migrate all tool imports to direct child access, (3) split/rename the 6 lifecycle tools, (4) remove `CANNOT_DELETE_DEFAULT` guard, (5) update all tests.

## Architecture Patterns

### Current Tool Registration Pattern (unchanged)
Every tool follows this exact pattern — new tools MUST follow it too:
```typescript
// src/tools/my-tool.ts
import { z } from 'zod';
import type { McpServer } from '@modelcontextprotocol/sdk/server/mcp.js';
import { makeSuccess } from '../types/envelope.js';
import { resolveProjectSafely, returnError } from './tool-helpers.js';
import { TOOL_DESCRIPTIONS, PARAMS } from './descriptions.js';
import { logger } from '../logging/logger.js';

export function registerMyTool(server: McpServer): void {
	server.registerTool(
		'my_tool',
		{
			title: 'My Tool',
			description: TOOL_DESCRIPTIONS.my_tool,
			inputSchema: {
				project: PARAMS.project,
				// tool-specific params...
			},
		},
		async ({ project, ...params }) => {
			logger.debug('my_tool called', { project, ...params });

			const resolved = resolveProjectSafely(project);
			if (!resolved.ok) return resolved.error;
			const loadedProject = resolved.project;

			// tool logic...

			const envelope = makeSuccess({ /* data */ }, {
				provenance: { tool: 'my_tool', project: loadedProject.name },
			});

			return {
				content: [{ type: 'text' as const, text: 'human-readable summary' }],
				structuredContent: envelope,
			};
		},
	);
}
```

### Pattern 1: Compat Migration — getRootPath Replacement
**What:** Replace `getRootPath(project)` calls with direct child access
**When to use:** Every tool that currently imports from compat.ts

The current compat `getRootPath` calls `getSoleFabricMod(project).rootPath`. The scope-aware replacement pattern already exists in `tool-helpers.ts` and `resolve-symbol-position.ts`:

```typescript
// BEFORE (compat):
import { getRootPath } from '../project/compat.js';
const rootPath = getRootPath(loadedProject);

// AFTER (direct, scope-aware):
// When scope is available (most tools already have it):
const child = scope ? loadedProject.children.get(scope) : undefined;
const rootPath = child?.kind === 'fabric-mod' ? child.rootPath : undefined;
// Or when rootPath is needed for createSourceAdapter, handle at getDependenciesForTool level
```

**Key insight:** `rootPath` is only needed for `createSourceAdapter` which reads mod source (category 'mod-source'). The `getDependenciesForTool` function already handles scope-aware dependency resolution. The `resolveClassSource` and `resolveSymbolPosition` functions in `tool-helpers.ts` are the only places that use `rootPath` directly — they need the same scope-aware pattern.

### Pattern 2: Tool Splitting — load_project into create_project + add_fabric_mod
**What:** The current `load_project` has two code paths (lines 33-93: add to existing project, lines 94-187: create new project + JDT LS init). Split these into two tools.
**Key detail:** `create_project` creates an empty named container. `add_fabric_mod` adds a fabric mod child to an existing project. The JDT LS initialization logic stays in `add_fabric_mod` (triggered when adding to a project with no existing JDT LS session).

```typescript
// create_project: Simple — creates empty project in store
const project: Project = { name: targetName, children: new Map() };
projectStore.set(targetName, project);

// add_fabric_mod: Current load_project "add to existing" path
// Includes: loadFabricMod(), collision resolution, jar registration, JDT LS init if first child
```

### Pattern 3: Tool Splitting — unload_project into remove_project + remove_project_member
**What:** Current `unload_project` has two paths: scoped (remove child, lines 36-125) and full (remove project, lines 127-159). Split into separate tools.
**Key detail:** `remove_project_member` handles both fabric mods AND study jars (replacing `remove_study_jar`). The child type determines cleanup behavior.

### Pattern 4: Tool Splitting — get_project_metadata into get_project_info + get_member_info
**What:** Current `get_project_metadata` has scoped and unscoped paths. Split so `get_project_info` returns project overview with member summaries, and `get_member_info` returns detailed info for a specific member.
**Key detail:** `get_project_info` should NOT call compat functions — iterate `project.children` directly, returning name, kind, and basic metadata per child.

### Pattern 5: Tool Splitting — refresh_dependencies into refresh_project + refresh_project_members
**What:** Current `refresh_dependencies` uses `scope` to choose between all-mods and single-mod refresh. Split into two tools: `refresh_project` (always refreshes all), `refresh_project_members` (requires explicit member names array).
**Key detail:** `refresh_project_members` takes `members: string[]` not `scope: string`. An empty array is not an error but returns "nothing changed".

### Pattern 6: Rename Propagation
**What:** `defaultProject` -> `activeProject`, `defaultChild` -> `activeChild`
**Where it touches:**
- `src/state/project-store.ts`: field name `defaultProject` -> `activeProject`, methods `setDefault`/`getDefault` -> `setActive`/`getActive`
- `src/project/types.ts`: `Project.defaultChild` -> `Project.activeChild`
- `src/project/namespace-resolver.ts`: `project.defaultChild` reference
- `src/tools/set-default-project.ts` -> `src/tools/set-active-project.ts` (file rename + tool name)
- `src/tools/descriptions.ts`: `set_default_project` -> `set_active_project`
- Error messages: "set_default_project" -> "set_active_project"
- All tests referencing these names

### Anti-Patterns to Avoid
- **Partial compat removal:** Do NOT leave any imports from `compat.ts` — the file must be fully deleted. Grep verify.
- **Mixed old/new tool names:** After migration, no tool should be registered with old names. The tool index must register only new names.
- **Leaving LoadedProject references:** Replace all `LoadedProject` with `Project` in imports and type annotations.
- **Leaving CANNOT_DELETE_DEFAULT:** The compat-era guard preventing deletion of the 'default' project must be removed. Projects are now freely deletable.

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|

## Common Pitfalls

### Pitfall 1: Dangling compat imports
**What goes wrong:** A tool file still imports from `../project/compat.js` after deletion, causing compile error.
**Why it happens:** 14 tool files import compat functions. Easy to miss one.
**How to avoid:** After deleting compat.ts, run `npx tsc --noEmit` to catch all broken imports. Also grep for `from '../project/compat` and `from '../../project/compat`.
**Warning signs:** TypeScript compilation errors mentioning compat.js.

### Pitfall 2: Stale tool name in descriptions.ts
**What goes wrong:** New tool registered with name X but `TOOL_DESCRIPTIONS` still has old name Y, or missing entirely.
**Why it happens:** descriptions.ts is a separate file that must be updated in sync with tool registration changes.
**How to avoid:** Update `TOOL_DESCRIPTIONS` object and `SERVER_INSTRUCTIONS` text in descriptions.ts when adding/renaming/removing tools.
**Warning signs:** Runtime error "Cannot read property of undefined" when accessing `TOOL_DESCRIPTIONS.new_tool_name`.

### Pitfall 3: Forgetting to update tool index.ts
**What goes wrong:** New tool exists but is never registered because index.ts still imports old registration function.
**Why it happens:** index.ts has explicit import+call for each tool.
**How to avoid:** Update `src/tools/index.ts` — remove old imports/calls, add new ones. Verify tool count matches expectations.
**Warning signs:** Tool not appearing in MCP tool list.

### Pitfall 4: resolveClassSource/resolveSymbolPosition rootPath fallback
**What goes wrong:** When compat is removed, the `getRootPath(loadedProject)` fallback in these functions breaks. Without scope and with multiple children, there's no single rootPath.
**Why it happens:** These functions use rootPath for `createSourceAdapter` on mod-source entries.
**How to avoid:** When iterating all dependencies via `getDependenciesForTool`, the rootPath should come from the child that owns each dependency. For mod-source deps, match the dep ID prefix to the child name.
**Warning signs:** Mod source reads failing in multi-mod projects.

### Pitfall 5: CANNOT_DELETE_DEFAULT still blocking
**What goes wrong:** After removing compat, the `delete()` method in ProjectStore still throws when deleting the 'default' project.
**Why it happens:** This guard was added during compat era. The message literally says "during compatibility mode."
**How to avoid:** Remove the guard in ProjectStore.delete(). Update the corresponding test.
**Warning signs:** "Cannot delete the 'default' project during compatibility mode" error at runtime.

### Pitfall 6: Error messages referencing old tool names
**What goes wrong:** Error suggestions say "use load_project" or "use set_default_project" after those tools are renamed.
**Why it happens:** DomainError suggestions and returnError calls throughout the codebase reference tool names by string.
**How to avoid:** Grep for old tool names in error messages: `load_project`, `unload_project`, `set_default_project`, `get_project_metadata`, `refresh_dependencies`, `remove_study_jar`.
**Warning signs:** Error responses suggesting tools that no longer exist.

### Pitfall 7: ProjectStore error messages referencing old tool names
**What goes wrong:** `ProjectStore.resolveProject()` suggests "use set_default_project" and `ProjectStore.set()` suggests "unload the existing project" — both reference old concepts.
**Why it happens:** These error messages were written before the rename.
**How to avoid:** Update suggestion strings in `project-store.ts` to reference `set_active_project`, `remove_project`, etc.
**Warning signs:** Stale tool name suggestions in DomainError responses.

### Pitfall 8: SERVER_INSTRUCTIONS text in descriptions.ts
**What goes wrong:** The workflow instructions at the top of descriptions.ts still say "Load a project with load_project" and reference old tool names.
**Why it happens:** SERVER_INSTRUCTIONS is a large text block that's easy to overlook.
**How to avoid:** Rewrite SERVER_INSTRUCTIONS to reflect new tool taxonomy.
**Warning signs:** LLM clients receiving outdated workflow guidance.

### Example 2: Replacing getSoleFabricMod in configure-filters
```typescript
// BEFORE:
import { getSoleFabricMod } from '../project/compat.js';
mod = getSoleFabricMod(loadedProject);

// AFTER (scope-aware, already half-implemented in the tool):
if (scope) {
	const child = loadedProject.children.get(scope);
	if (!child || child.kind !== 'fabric-mod') {
		return returnError('CHILD_NOT_FOUND', ...);
	}
	mod = child;
} else {
	// Find sole fabric mod or error
	let found: FabricModChild | undefined;
	for (const child of loadedProject.children.values()) {
		if (child.kind === 'fabric-mod') {
			if (found) {
				return returnError('AMBIGUOUS_CHILD', 'Multiple fabric mods — specify scope', ...);
			}
			found = child;
		}
	}
	if (!found) {
		return returnError('NO_FABRIC_MOD', ...);
	}
	mod = found;
}
```

### Example 3: create_project tool (new)
```typescript
export function registerCreateProjectTool(server: McpServer): void {
	server.registerTool(
		'create_project',
		{
			title: 'Create Project',
			description: TOOL_DESCRIPTIONS.create_project,
			inputSchema: {
				name: z.string().describe('Name for the new project'),
			},
		},
		async ({ name }) => {
			logger.debug('create_project called', { name });

			const project: Project = { name, children: new Map() };
			try {
				projectStore.set(name, project);
			} catch (error) {
				if (error instanceof Error && 'code' in error) {
					const de = error as any;
					return returnError(de.code, de.message, de.tried ?? [], de.suggestions);
				}
				throw error;
			}

			const envelope = makeSuccess({ name }, {
				provenance: { tool: 'create_project', project: name },
			});

			return {
				content: [{ type: 'text' as const, text: `Created project '${name}'` }],
				structuredContent: envelope,
			};
		},
	);
}
```

### Example 5: resolveClassSource rootPath fix
```typescript
// BEFORE (compat-dependent):
const rootPath = scope
	? (() => { const c = loadedProject.children.get(scope); return c?.kind === 'fabric-mod' ? c.rootPath : getRootPath(loadedProject); })()
	: getRootPath(loadedProject);

// AFTER (fully native):
function getRootPathForDep(project: Project, depId: string, scope?: string): string | undefined {
	// If scoped, use that child's rootPath
	if (scope) {
		const child = project.children.get(scope);
		return child?.kind === 'fabric-mod' ? child.rootPath : undefined;
	}
	// Match dep ID prefix to child name for mod-source deps
	for (const [name, child] of project.children) {
		if (child.kind === 'fabric-mod') {
			if (depId === name || depId.startsWith(name + '/')) {
				return child.rootPath;
			}
		}
	}
	return undefined;
}
```

## Open Questions

1. **rootPath resolution in multi-mod unscoped mode**
   - What we know: `resolveClassSource` and `resolveSymbolPosition` need rootPath for mod-source deps. Currently uses compat fallback.
   - What's unclear: In unscoped mode with multiple children, which rootPath to use when iterating all deps?
   - Recommendation: Match dep ID prefix to child name. Each dep in `getDependenciesForTool` already has a namespaced ID like `modA/minecraft` — extract `modA`, find child, use its rootPath. For mod-source entries (bare child name), match directly.

2. **list_projects simplification scope**
   - What we know: CONTEXT says "simplified to return project names, member counts, active child." Current version shows MC version, mapping era, rootPath per project.
   - What's unclear: How much to simplify — does it still show per-member details or just counts?
   - Recommendation: Return `{ name, memberCount, activeChild, isActive }` per project. If the caller needs details, they use `get_project_info`.

3. **getDependenciesForTool — keep or split?**
   - What we know: Marked as Claude's discretion. Currently handles both scoped and unscoped cases.
   - What's unclear: Whether splitting would improve clarity.
   - Recommendation: Keep as-is. It's 55 lines, well-documented, and already handles all cases correctly. The scope parameter naturally maps to the new tool separation.
