<objective>
Extend refresh_project and refresh_project_members to re-parse build configuration files (gradle.properties, build.gradle.kts, fabric.mod.json) before re-discovering dependencies, so that changes to Minecraft version, mappings, or mod metadata are detected without requiring project removal and re-creation.

Purpose: Currently both refresh tools pass stale `mod.gradleConfig`, `mod.sourcesJar.path`, and `mod.fabricMod` to `discoverDependencies()`. After a user edits their build files, refreshing does nothing useful. This plan fixes that.

Output: A shared `reloadFabricModConfig()` helper in `loader.ts` and updated refresh tools that call it before dependency discovery.
</objective>

  <name>Task 1: Extract reloadFabricModConfig helper in loader.ts</name>
  <files>src/project/loader.ts, tests/project/loader.test.ts</files>
  <behavior>
    - Test 1: reloadFabricModConfig re-reads gradle.properties and build.gradle.kts from rootPath, updates mod.gradleConfig
    - Test 2: reloadFabricModConfig resolves new sources jar path and updates mod.sourcesJar (path + exists)
    - Test 3: reloadFabricModConfig re-reads fabric.mod.json and updates mod.fabricMod
    - Test 4: When minecraftVersion changes, returned warnings include version change message
    - Test 5: When fabric.mod.json id changes, returned warnings include mod ID change message (and mod.name stays unchanged)
    - Test 6: When new sources jar path does not exist on disk, mod.sourcesJar.exists = false and returned warnings include genSources suggestion
    - Test 7: When gradle.properties or build.gradle.kts is missing, throws DomainError (same as loadFabricMod)
  </behavior>
  <action>
Create an exported async function `reloadFabricModConfig(mod: FabricModChild)` in `src/project/loader.ts` that:

1. Reads `gradle.properties` from `mod.rootPath` via `readFile()` and parses with `parseGradleProperties()`. Throws DomainError if file missing (reuse same error codes as loadFabricMod).
2. Reads `build.gradle.kts` from `mod.rootPath` via `readFile()` and parses with `parseBuildGradle(content, properties)`. Throws DomainError if file missing.
3. Calls `resolveSourcesJarPath(newGradleConfig)` to get the new path.
4. Checks if new sources jar exists on disk via `access()`. Sets `exists` accordingly (does NOT throw if missing — unlike loadFabricMod).
5. Reads `fabric.mod.json` from `mod.rootPath/src/main/resources/fabric.mod.json` and parses with `parseFabricMod()`. Throws DomainError if file missing.
6. Compares old vs new values and builds a `warnings: string[]` array:
   - If `mod.gradleConfig.minecraftVersion !== newGradleConfig.minecraftVersion`: push `"Minecraft version changed from {old} to {new} — sources jar path updated"`
   - If `mod.fabricMod.id !== newFabricMod.id`: push `"fabric.mod.json id changed from '{old}' to '{new}' — child name kept as '{old}' for namespace stability"`
   - If sources jar does not exist: push `"New sources jar not found. Run ./gradlew genSources, then refresh again."`
7. Mutates `mod` in place: `mod.gradleConfig = newGradleConfig`, `mod.sourcesJar = { path: newPath, exists }`, `mod.fabricMod = newFabricMod`.
8. Returns `{ warnings: string[] }`.

The helper reuses the `fileExists()` function already in loader.ts. Extract the file-reading patterns from `loadFabricMod()` — the logic is nearly identical but the error behavior for missing sources jar differs (warn vs throw).

For tests, mock `fs/promises` (readFile, access) to control file contents. Create a fake `FabricModChild` with known old values, call `reloadFabricModConfig`, and assert:
- mod fields are updated to new values
- warnings array contains expected messages for each change scenario
- DomainError thrown for missing required files
  </action>

   ```typescript
   // Re-parse build configuration files
   const reloadResult = await reloadFabricModConfig(mod);
   ```
   This must happen before closing old handles because `mod.sourcesJar.path` may change and the old path needs to be captured first. So the call order is:
   - Save old dependency list (`const oldDeps = mod.dependencyJars`)
   - Collect old jar paths into `oldJarPaths` set (uses current `mod.sourcesJar.path`)
   - Call `reloadFabricModConfig(mod)` — mutates mod.gradleConfig, mod.sourcesJar, mod.fabricMod
   - Close old jar handles (uses `oldJarPaths`)
   - Call `discoverDependencies(mod.gradleConfig, mod.sourcesJar.path, ...)` — now uses UPDATED config
   - Rest of the existing flow unchanged
