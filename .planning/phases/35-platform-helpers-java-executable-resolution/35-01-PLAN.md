<objective>
Create `src/platform/index.ts` — a new pure (no I/O) cross-cutting module exporting five platform-branched helpers consumed by Phase 35 (and later Phases 36/37/38). All exports must be strongly typed. Unix branches MUST return today's literals verbatim (UNIX-01 commitment). Windows branches use `path.win32.join` where separator correctness matters so cross-host tests assert exact strings.

Purpose: This is the foundation of v1.6 Windows Support. Without `javaBinaryName()` / `javaBinaryInHome()`, Phase 35's `detectJava` wiring (Plan 02) cannot resolve to platform-correct candidate strings, and Windows `spawn` continues to ENOENT on `C:\...\bin\java`.

Output: One new source file (`src/platform/index.ts`, ~80 LOC) and one new test file (`tests/platform/index.test.ts`) exercising both branches of all four functions.
</objective>

// src/platform/index.ts
export const isWindows: boolean;                          // process.platform === 'win32'
export function javaBinaryName(): string;                 // 'java.exe' on win32, 'java' elsewhere
export function javaBinaryInHome(javaHome: string): string; // path.win32.join(home, 'bin', 'java.exe') on win32; path.posix.join(home, 'bin', 'java') elsewhere

- `jdtlsCandidateDirs()` Unix → `[join(homedir(), '.local', 'share', 'jdtls'), '/usr/local/share/jdtls', join(homedir(), 'jdtls')]`

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user → `process.env` (`LOCALAPPDATA`, `ProgramFiles`, `JAVA_HOME`) | User-controlled environment variables flow into path construction in `jdtlsCandidateDirs()` and `commonJavaLocations()`. These values are used to build candidate paths probed in later phases — they do NOT exec arbitrary code in Phase 35. |
| user → CLI `--java-home` argument (handled in Plan 02, not here) | Out of scope for Plan 01. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-35-01 | Tampering | `process.env.LOCALAPPDATA` / `ProgramFiles` read by `jdtlsCandidateDirs()` | accept | These are standard Windows env vars set by the OS. If an attacker can set them in our process environment, they can already exec arbitrary code; the candidate paths are PROBED (existsSync in Phase 38) not exec'd. ASVS L1 acceptable. Fallback to fixed literals (`'C:\\Program Files'` etc.) on missing env, so missing vars never become empty-string traversals. |
| T-35-02 | Information Disclosure | `homedir()` returns the user's home path which appears in candidate path strings | accept | Already disclosed throughout the codebase (`process.env.HOME` was used in v1.5 `findJdtLs`). No new exposure. |
| T-35-03 | Tampering | `commonJavaLocations()` returns parent dirs that Phase 37 will glob and exec for version probes | accept (deferred) | Plan 01 ships only data; the exec/glob attack surface is Phase 37's concern. Phase 37 must validate each candidate via `--version` probe before trusting. Documented in milestone PITFALLS.md §Security Mistakes. |

No new packages installed → no Package Legitimacy gate needed. RESEARCH.md confirms zero external dependencies for Phase 35.
</threat_model>
