<objective>
Wire `src/platform/index.ts` (from Plan 01) into `src/jdtls/client.ts`'s `detectJava` candidate loop and add a new exported `resolveJavaExecutable(candidate)` helper that converts absolute Java paths into files `child_process.spawn` can actually exec on Windows (libuv does not honor PATHEXT for absolute paths). Augment `tests/jdtls/client.test.ts` with three new `describe` blocks covering `resolveJavaExecutable` on Windows, `resolveJavaExecutable` on Unix (UNIX-01 passthrough), and `detectJava` end-to-end on mocked Windows.

Purpose: This is the actual bug fix. Today, `detectJava` succeeds on Windows via `execSync` → `cmd.exe` → PATHEXT, then `startJdtLs` fails immediately with `spawn ENOENT` on the same path because `spawn` calls `CreateProcessW` directly without PATHEXT resolution. After this plan, the `javaPath` returned by `detectJava` is `.exe`-resolved (existence-checked) on Windows and unchanged on Unix.

Output: Modified `src/jdtls/client.ts` (one new helper, two-line edit to `detectJava` candidate construction, one-line edit to the candidate-loop variable handling) and extended `tests/jdtls/client.test.ts` (existing tests untouched, three new describes added).
</objective>

```typescript
export function resolveJavaExecutable(candidate: string): string | null;
```

Behavior:
- Bare name (no `/` and no `\`): return candidate unchanged (libuv handles PATHEXT for PATH lookups in spawn — verified per RESEARCH.md Assumption A1, milestone PITFALLS.md PITFALL-1 §"Bare 'java' is the one case where Windows DTRT").

- Unix + path with separator: return candidate as-is, NO `existsSync` call. UNIX-01 commitment — existing v1.5 tests use fake paths that don't exist on disk; any existsSync gate would break them.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user → `process.env.JAVA_HOME` / `--java-home` CLI flag | User-controlled string flows into `javaBinaryInHome(javaHome)` and ultimately to `child_process.spawn` (in `startJdtLs`, not Phase 35 code). Already-existing trust boundary in v1.5; Phase 35 makes it Windows-functional. |
| filesystem → `existsSync` probe results | TOCTOU window between `resolveJavaExecutable`'s `existsSync` and `startJdtLs`'s `spawn`. Sub-millisecond on the same path. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-35-04 | Elevation of Privilege | User-controlled `JAVA_HOME` points to attacker-controlled binary | accept | Already-existing risk in v1.5 — server runs whatever Java binary the user configures. Phase 35 just makes Windows able to spawn it. The `--version` `execSync` probe in `detectJava` (UNCHANGED in this plan) rejects non-Java binaries by failing to parse version output and falling through to the next candidate. ASVS L1 sufficient for an MCP server running with user privileges. RESEARCH.md "Security Domain" confirms no new mitigation needed. |
| T-35-05 | Tampering | TOCTOU race between `existsSync(candidate + '.exe')` in `resolveJavaExecutable` and `spawn(javaPath, ...)` in `startJdtLs` | accept | Sub-millisecond window on the same path; no realistic attack vector for a local MCP server. Even if a race occurred, `spawn` would fail with ENOENT and the server would surface a clean error. Documented in RESEARCH.md "Pitfall 5" and milestone PITFALLS.md §Security Mistakes. |
| T-35-06 | Tampering | Path-traversal via crafted `--java-home` value (e.g., `'../../../etc/passwd'`) flowing into `javaBinaryInHome` | accept | `path.win32.join` / `path.posix.join` normalize but do NOT block `..` segments. The `--version` `execSync` probe rejects non-Java binaries. Phase 37 will add an explicit `existsSync` + version check at the JDK-home level for further hardening. No new mitigation in Phase 35. |
| T-35-SC | Tampering | npm/pip/cargo installs | not applicable | RESEARCH.md "Package Legitimacy Audit" confirms zero new packages in Phase 35. No install tasks → no slopcheck needed. |

No package installs → no `T-35-SC` enforcement task needed. All threats accepted with rationale; ASVS L1 considered sufficient for this trust model (local-only MCP server running with user privileges).
