Create `src/tools/list-packages.ts` following the established tool pattern (see get-project-metadata.ts):

Tool name: `list_packages`
Title: `List Packages`
Description: `List Java packages in source jars and mod source. Supports filtering by jar and drilling into sub-packages.`

Zod input schema:
```typescript
project: z.string().optional().describe('Project name (optional if only one project loaded or default is set)'),
jars: z.array(z.string()).optional().describe('Jar IDs or glob patterns to scope to (default: all jars)'),
package: z.string().optional().describe('Parent package to list children of (default: top-level packages)'),
depth: z.number().int().min(1).optional().describe('How many levels deep to list (default: 1)'),
```

Handler logic:
1. `resolveProject(project)` with standard DomainError catch pattern
2. `getFilteredDependencies(project.dependencyJars, project.filterConfig)` to get filtered jars
3. If `jars` param provided, further filter using `picomatch(jars)` against jar IDs
4. For each matching jar with `available: true` (or id === 'src'):
   a. Create source adapter via `createSourceAdapter(jarReader, dep, project.rootPath)`
   b. Get entries via `adapter.listJavaEntries()`
   c. Build `EntryIndex` from entries
   d. Get packages via `index.getPackages(package, depth)` 
5. Merge packages across jars: same package name -> union jars arrays, sum class counts
6. Sort packages alphabetically by name
7. Return `makeSuccess({ packages: PackageEntry[] }, { provenance: { tool: 'list_packages', project: project.name } })`
8. Response format per CONTEXT.md: dual `content` (text JSON) + `structuredContent`

Cache: Store built EntryIndex per jar path in a module-level `Map<string, EntryIndex>` to avoid rebuilding on repeated calls. Clear on project unload (not in scope of this tool, but design the cache as a simple Map that can be cleared).

Tool name: `list_classes`
Title: `List Classes`
Description: `List Java classes in a package with metadata (access, modifiers, type) and nested inner classes. Supports filtering by jar.`

Zod input schema:
```typescript
project: z.string().optional().describe('Project name (optional if only one project loaded or default is set)'),
jars: z.array(z.string()).optional().describe('Jar IDs or glob patterns to scope to (default: all jars)'),
package: z.string().describe('Fully-qualified package name to list classes from (required)'),
depth: z.number().int().min(1).optional().describe('Include classes from sub-packages up to this depth (default: 1, this package only)'),
```

Handler logic:
1. Same project resolution and jar filtering as list_packages
2. For each matching jar:
   a. Create source adapter, get entries, build EntryIndex (reuse cached index)
   b. Get classes via `index.getClasses(packageName)` (and sub-packages if depth > 1)
   c. For each class, read first 4KB via `adapter.readEntry(entryPath)` and parse with `parseClassDeclaration`
   d. For each inner class (from index), read its entry and parse metadata too
3. Build ClassEntry objects per CONTEXT.md JSON structure:
   ```json
   {
     "name": "MinecraftClient",
     "access": "public",
     "modifiers": [],
     "type": "class",
     "jars": ["minecraft"],
     "innerClasses": [
       {
         "name": "MinecraftClient$Options",
         "access": "public",
         "modifiers": ["static"],
         "type": "class"
       }
     ]
   }
   ```
4. Merge classes across jars: same FQN -> union jars arrays, merge inner class lists
5. Sort by class name alphabetically
6. Return `makeSuccess({ classes: [...] }, { provenance: { tool: 'list_classes', project: project.name, package: packageName } })`

Note on entry path construction: For a class `net.minecraft.client.MinecraftClient`, the entry path is `net/minecraft/client/MinecraftClient.java`. For inner class `MinecraftClient$Options`, entry path is `net/minecraft/client/MinecraftClient$Options.java`.

Create `src/tools/read-source.ts`:

Tool name: `read_source`
Title: `Read Source`
Description: `Read the full source code of a Java class by fully-qualified name. Returns source from all matching jars with provenance when no specific jar is specified.`

Zod input schema:
```typescript
project: z.string().optional().describe('Project name (optional if only one project loaded or default is set)'),
jar: z.string().optional().describe('Specific jar ID to read from (default: search all jars)'),
class: z.string().describe('Fully-qualified class name using dot notation (e.g., net.minecraft.client.MinecraftClient)'),
```

Handler logic:
1. `resolveProject(project)` with standard DomainError catch pattern
2. Convert FQN to entry path: replace `.` with `/`, append `.java`. For inner classes containing `$`, the `$` stays in the filename: `net.minecraft.client.MinecraftClient$Options` -> `net/minecraft/client/MinecraftClient$Options.java`
3. If `jar` is specified:
   a. Find the DependencyEntry by ID in `project.dependencyJars`
   b. If not found or not available, return `makeError('JAR_NOT_FOUND', ...)`
   c. Create source adapter, read entry, return single result
4. If `jar` is omitted:
   a. Get filtered dependencies via `getFilteredDependencies`
   b. Sort by priority: minecraft first, then src, then remaining sorted alphabetically
   c. For each jar, try to read the entry path
   d. Collect ALL successful reads (not just first match)
   e. If none found, return `makeError('CLASS_NOT_FOUND', ...)`
5. Response data structure:
   ```typescript
   {
     sources: Array<{
       jar: string;           // jar ID
       category: JarCategory; // "minecraft", "mod-source", "fabric-api", "library"
       provenanceChains: string[][];
       source: string;        // full source text (UTF-8)
       lineCount: number;     // number of lines
     }>
   }
   ```
6. Return `makeSuccess(data, { provenance: { tool: 'read_source', project: project.name, class: className } })`
7. Dual `content` + `structuredContent` response
