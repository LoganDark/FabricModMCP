# Phase 25.1: Rework tools and tests for native architecture - Context

**Gathered:** 2026-04-15
**Status:** Ready for planning

<domain>
## Phase Boundary

Remove all compatibility shims (compat.ts, LoadedProject alias). Rework tools to natively use Project/FabricModChild/StudyJarChild types. Cleanly separate project creation, member addition, and operations within projects/members. Rename default→active terminology. Breaking existing clients is acceptable (all clients are LLMs).

</domain>

<decisions>
## Implementation Decisions

### Tool taxonomy — project lifecycle
- `create_project` — new tool, creates empty project container (name only)
- `remove_project` — renamed from `unload_project`, project-level only (no more scoped child removal)
- `list_projects` — simplified to return project names, member counts, active child
- `get_project_info` — reworked from unscoped `get-project-metadata`, returns project overview with basic member summaries (enough info to call `get_member_info` for details)
- `set_active_project` — renamed from `set_default_project`

### Tool taxonomy — member lifecycle
- `add_fabric_mod` — new tool, adds fabric mod child to existing project (replaces `load_project`)
- `add_study_jar` — stays as-is
- `remove_project_member` — new tool, removes any child (fabric mod or study jar) by name. Replaces scoped `unload_project` and `remove_study_jar`
- `get_member_info` — reworked from scoped `get-project-metadata`, returns detailed info for a specific member
- `set_active_child` — new tool, sets active child on a project (like `set_active_project` but for children)
- `configure_study_jar` — stays as-is
- `list_study_jars` — stays as-is
- `configure_filters` — stays as-is (scope-aware)

### Tool taxonomy — refresh operations
- `refresh_project` — renamed from unscoped `refresh_dependencies`, refreshes all members' deps, takes no member name
- `refresh_project_members` — renamed from scoped `refresh_dependencies`, requires a set of member names. Empty set is not an error but returns "nothing changed"

### Tools removed
- `load_project` — replaced by `create_project` + `add_fabric_mod`
- `remove_study_jar` — redundant with `remove_project_member`
- `unload_project` — split into `remove_project` + `remove_project_member`

### Naming renames
- `defaultProject` → `activeProject` throughout codebase (ProjectStore, tools, tests)
- `defaultChild` → `activeChild` throughout codebase (Project type, tools, tests)
- `set_default_project` tool → `set_active_project`

### Compat layer removal
- Delete `src/project/compat.ts` entirely (all 8 functions: getSoleFabricMod, getGradleConfig, getSourcesJar, getFabricMod, getDependencyJars, getFilterConfig, getRootPath, getStudyJars)
- Delete `tests/project/compat.test.ts`
- Remove `LoadedProject` type alias from `src/project/types.ts`
- All 14 tool files that import compat functions must be migrated to direct child access

### No-scope behavior with multiple children
- Jar-aware browsing tools without scope operate on ALL children (union of all deps) — project-wide operation
- If implementing union behavior is significantly complex, error for now and defer to Phase 26
- Scope is required for single-item reads (e.g., `read_source` on mod source) when multiple members exist
- Study jars are project-level and always included in project-wide operations (unchanged)

### Provenance in results
- Namespaced jar IDs (`my-mod/minecraft`) are sufficient for provenance — no additional scope field needed
- Results already include namespaced jar IDs from Phase 24

### Active child / active project semantics
- `activeChild` is never auto-set — caller sets it explicitly via `set_active_child`
- When `activeChild` is set, bare jar IDs resolve within that child's namespace
- When only one child exists, bare IDs resolve to that child regardless of `activeChild`
- Same semantics as current `defaultChild`/`defaultProject`, just renamed

### Test migration
- All tests must use new tool names and native types directly
- Test factories (`makeFakeProject`, `makeFakeFabricMod`, etc.) already produce new types — keep them
- Remove any test code that relies on compat accessors

### Claude's Discretion
- Order of migration steps (which tools to rework first)
- Internal helper refactoring in `tool-helpers.ts` to replace compat patterns
- Error message wording for scope-required situations
- Whether to split `tool-helpers.ts` getDependenciesForTool or keep it as the central dispatch

</decisions>

<specifics>
## Specific Ideas

- The term "project member" covers both fabric mods and study jars — use this in tool descriptions and error messages
- `get_project_info` should return enough that an LLM can immediately call `get_member_info` with the right member name
- `refresh_project_members` with an empty set should succeed with a "nothing changed" response, not error
- Breaking clients is fine — all clients are LLMs and will adapt to new tool names and schemas

</specifics>

<code_context>
## Existing Code Insights

### Reusable Assets
- `getDependenciesForTool()` in tool-helpers.ts: Already scope-aware, central dispatch — needs compat fallback removed but structure is sound
- `resolveJarId/resolveJarIds` in namespace-resolver.ts: Already handle scope, activeChild, sole-child inference
- Test factories: Already produce new-architecture types, need no structural changes
- `makeFakeMultiModProject`: Ready for multi-mod test scenarios

### Established Patterns
- Tools use `resolveProjectSafely()` → `projectStore.resolveProject()` for project resolution
- Scope parameter on all 17 jar-aware tools from Phase 24
- `DomainError` for error reporting with code, message, tried, suggestions
- Study jar tools already use direct child access (no compat)

### Integration Points
- Every tool importing from `compat.ts` needs migration to direct `project.children.get(scope)` access
- `tool-helpers.ts` mixed-mode pattern (`scope ? directAccess : getRootPath(project)`) is the primary pattern to eliminate
- `ProjectStore` needs `defaultProject` → `activeProject` rename
- `Project` type needs `defaultChild` → `activeChild` rename
- Tool registration in `src/tools/index.ts` needs new tools added and old tools removed

</code_context>
