In the "Apply removals" loop, BEFORE the existing `loadedProject.studyJars.delete(name);` line, add the workspace unsync call. The loop becomes:

```typescript
for (const name of names) {
	const studyJar = loadedProject.studyJars.get(name)!;
	await unsyncStudyJarFromWorkspace(name, loadedProject.jdtls);
	await jarReader.removeProjectJar(loadedProject.name, studyJar.jarPath);
	evictEntryIndex(studyJar.jarPath);
	loadedProject.studyJars.delete(name);
}
```

The unsync goes first because it needs to update the JDT LS workspace BEFORE the jar handle is removed. Order: (1) unsync from workspace (deletes extracted dir, updates classpath, notifies JDT LS), (2) remove jar handle, (3) evict entry index cache, (4) delete from studyJars map.

```typescript
text: `Removed ${names.length} study jar(s): ${names.join(', ')}`
```
Change to:
```typescript
text: `Removed ${names.length} study jar(s): ${names.join(', ')}. Semantic navigation results have been updated.`
```

This implements the locked decision: "`remove_study_jar` response mentions that semantic navigation results have been updated." Note: per locked decision, `remove_study_jar` does NOT warn about JDT LS unavailability — the `unsyncStudyJarFromWorkspace` function silently returns `{ synced: false }` when JDT LS is unavailable, and we don't check or display that result.
